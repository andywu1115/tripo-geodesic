# Tripo 3D Mesh Geodesic Pathfinding and Spatial Analysis Engine

CSE 20312 final project. Loads a 3D mesh generated by the Tripo AI API,
builds a weighted surface graph from its triangles, and computes shortest
surface paths across it with a hand written min-heap and Dijkstra's
algorithm.

## Key points
### Data structures and algorithms
**MinHeap:** An array-backed binary heap extended from my HW09 solution:
`percolate_up`, `percolate_down`, `insert` and `remove`, each O(log N). The
only change the project needed was what the heap holds. HW09 stored integer
character frequencies; the Dijkstra frontier stores `(distance, vertex,
source)` tuples with float distances. Python compares tuples element by
element, so the comparison logic did not change at all: the distance orders
the heap and ties fall through to the vertex number.

**MeshAdjacencyGraph:** An adjacency list, `dict[int, dict[int, float]]`,
the same shape as the weighted graphs in EX33 and HW10B. Each triangle
contributes three undirected edges, stored in both directions, weighted by
`math.dist` between the endpoints. Writing a shared edge twice is harmless
because the second write stores the same value, which is what makes an edge
shared by two triangles count once.

**Vertex welding:** An `.obj` file writes a vertex once per texture or
normal seam, so geometrically identical corners arrive as different indices
and the surface would be shredded into pieces that look adjacent but share
no vertex. Rounding each coordinate to a grid of size 1e-6 turns "same
position" into dictionary key equality, which is O(1) per vertex and O(V)
overall. Measured on the densest mesh: 28,756 vertices in the file collapse
to 20,659 unique positions, which is exactly the count Tripo reported.

**Connected components:** Breadth-first search with the frontier and
visited pattern from HW10A. This mattered more than expected. Tripo
generated the island's trees as loose geometry that never touches the
terrain, so the two denser meshes have 271 and 263 separate components and
only 53% and 55% of their vertices belong to the island.

**Dijkstra with lazy deletion:** When a shorter route to a vertex is found,
a second entry is pushed rather than the existing one updated, and any
vertex popped after it has been settled is skipped. The heap can hold up to
E entries instead of V, which costs memory but keeps every heap operation
O(log V) with no index bookkeeping. A real `decrease_key` would need a
dictionary from each vertex to its position in the heap array.

**Path reconstruction:** HW10B uses a recursive generator with `yield
from`. The project walks the predecessor chain in a loop instead, because
each recursive call is a stack frame and a long path on a denser mesh could
reach Python's recursion limit.

**Complexity:** O((V + E) log V) time and O(V + E) space. E divided by V
measures 2.80, 2.91, 2.94 and 2.93 on the four meshes, so E is close to 3V
on a triangle mesh and the bound collapses to O(V log V).

### Coding
The `.obj` parser is written by hand rather than with a mesh library. It
reads `v` and `f` records and ignores everything else, handles 1-based and
negative vertex indices, strips the `v/vt/vn` field form, and fan
triangulates quads and n-gons into triangles.

`MeshAdjacencyGraph.neighbors` uses `dict.get(vertex, {})` rather than a
`defaultdict`, because reading a missing key from a `defaultdict` inserts
it, and inserting while walking the graph changes the dictionary's size
mid-iteration. I had already hit the same trap in HW10B's `flights.py`.

The solver takes its frontier as a parameter. That one change is what makes
the benchmark meaningful: the same algorithm runs on my heap or on `heapq`,
so the measured difference is the priority queue and nothing else.

41 unit tests across four modules, covering heap invariants after every
operation, parser edge cases through `io.StringIO` mock files, edge weights
against `math.dist`, welding, disconnected components, unreachable targets,
and agreement between the solver's reported distance and the edge weights
along the path it returns.

## Lessons learned
**The benchmark's real finding:** Swapping `heapq` into my own solver puts
it within 5 to 10% of networkx at every mesh size. My heap is 6.1 to 7.4
times slower. So the entire gap between my implementation and a tuned
library is the priority queue, not the algorithm, the adjacency list or the
relaxation loop. I would not have learned that from comparing against
networkx alone, because networkx differs in everything at once.

**A hypothesis that failed:** The island is a flat-bottomed solid, so I
expected shortest paths to cut underneath the terrain instead of following
it. I tested it by running the same endpoint pair on the full graph and on
a graph with the underside removed. The results were identical in every
figure: 1.2344 over 40 vertices, height 0.0303 to 0.1401 both times. The
base was never on a shortest route. What the height filter actually
prevents is narrower, which is the endpoint picker choosing vertices on the
underside, since the extreme points of an island along any horizontal axis
sit at the waterline.

**Rendering a path on a 3D surface:** This took four attempts.
matplotlib gives a `Line3D` and a `Poly3DCollection` one depth value each
and draws one wholly in front of the other, so the path kept disappearing.
Worse, the route runs through low coastal terrain between rock formations
taller than it is, so real geometry hides it from most camera angles too.
The fix was to stop asking one picture to do three jobs: a 3D view for what
the mesh is, a 2D plan view for where the route goes, and an elevation
profile for how it climbs.

**Mesh quality:** The Tripo export contains sliver triangles with zero
area, which make matplotlib divide by zero while computing lighting
normals. They are harmless to the graph, since a sliver still has three
edges of positive length and Dijkstra does not care about area.

**The four meshes are not one shape at four resolutions:** The two small
ones have a solid flat base and no trees; the two large ones have trees and
almost no base. The benchmark is still valid because it reports the largest
component size as V, but the meshes differ in structure and not only in
density.

**Terminal detail:** Long heredoc pastes were silently truncating, so a
file would appear to be created and not exist. Pasting one block at a time
and checking with `tail -3` before running anything saved a lot of
confusion.

## Use of AI
I used two AI tools in different roles: Gemini Notebook produced the one-page 
proposal in the planning lab, working from the course materials. Its reading of 
my homework schedule was correct.

Claude acted as a teaching assistant through the build. I ran every test and 
benchmark myself and pasted the real output back, and it was set up never to 
claim a test passed on output it had not seen. The core algorithms are not its work. 
The `MinHeap` logic is my HW09 solution, and the Dijkstra structure, the
predecessor dictionary and the lazy deletion all come from my HW10B
`flights.py`. I supplied both files and we diffed them against what was in
the repository rather than assuming they matched.

Three things are worth recording because they shaped how much I trusted it:
first, Claude initially contradicted the Gemini proposal on the homework
schedule, claiming HW09 was an AVL tree and that graph algorithms were
HW11B. It was working from a stale copy of the course schedule and was
wrong; Gemini had been right. It corrected itself once I loaded the current
schedule. The lesson is that a confident correction is not the same as an
accurate one.

Second, early on it told me it had reviewed my `heap.py` and found no
changes were needed. The logic did match  line for line but the claim 
was made before it could have been checked.  Then later a flaw was flagged.

Third, Claude predicted when it saw the proposal that the flat base would 
distort the geodesics and designed the height filter around that. The 
measurement disproved the prediction. The filter stayed because it still 
prevents a bad endpoint choice, and the negative result is in this README 
because it is a real finding.

I also made the design calls: which mesh to keep when the generated model did
not match the reference image, that the missing bay did not matter because
the crater already forces a detour, and that the three-panel figure needed
the 3D view back after Claude says to cut it. Two render attempts came back worse
than the one before, and I said so.

## Other notes
Critical code to review before the written and oral exams:
* `min_heap.py`, `percolate_up` and `percolate_down`. Know the comparison
  direction, why the scan checks the left child before the right, and why
  `remove` pops the last element before overwriting index 0 rather than
  after.
* `geodesic.py`, `compute_geodesic_field`. Be able to explain why skipping
  an already-settled vertex on pop is correct, how many entries the heap can
  hold under lazy deletion, and what a real `decrease_key` would require.
* `mesh_graph.py`, `_weld`. Why rounding to a grid gives O(V) and what a
  true nearest-neighbour merge would cost.
* `mesh_graph.py`, `walk` and `components`. The frontier and visited
  pattern, and why a `deque` pops from the left in O(1) while `list.pop(0)`
  is O(N).
* The complexity argument end to end: O((V + E) log V), why E is close to 3V
  on a triangle mesh, and why the measured seconds per V log V being flat is
  evidence for it.
